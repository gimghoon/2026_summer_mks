# 3편 — 배포와 기능 고도화

## 이 문서가 다루는 시기

이 문서는 로컬 MVP의 주요 실행 장애를 해결한 뒤, 표현 강도를 확장하고 Render에 배포하며 개인 컨텍스트 기능을 고도화한 과정부터 현재 상태까지를 시간순으로 기록한다.

### 1. 돌려 말하기 강도가 약하다고 평가했다

- 내가 요청하거나 한 행동: 실제 답장을 만들어 본 뒤 기존 최고 단계도 충분히 강하게 돌려 말하지 않는다고 평가했다.
- 확인한 내용: 초기 1~5단계는 직접 표현을 줄이는 정도였고, 사용자가 원한 비유·암시·여운 중심의 표현까지 도달하지 못했다.
- 바뀐 내용: 기존 강도 범위를 다시 정의하고 더 높은 단계가 별도의 창의성 규칙을 가져야 한다고 결정했다.
- 결과: 단순한 강도 조절을 넘어 창의적 우회 표현을 제품 기능으로 확장하는 작업이 시작됐다.

### 2. 우회 강도 6과 7을 추가했다

- 내가 요청하거나 한 행동: `완전 돌려 말하는 창의적인 버전`을 원하며 6·7단계를 추가해 달라고 했다.
- 확인한 내용: 6단계는 상황과 여운으로 강하게 우회하고, 7단계는 비유·장난스러운 암시·조용한 여운까지 활용하는 별도 정책이 필요했다.
- 바뀐 내용: 설정과 요청 스키마를 1~7로 확장했다. 6단계는 강한 우회, 7단계는 창의적인 완전 우회로 정의하고 프롬프트·정책·UI 설명·테스트를 함께 갱신했다.
- 결과: 사용자는 기존의 자연스러운 우회뿐 아니라 의도적으로 과감한 콘셉트 답장도 선택할 수 있게 됐다.

### 3. 6·7단계의 검증을 차단보다 주의로 바꾸라고 했다

- 내가 요청하거나 한 행동: 높은 단계에서는 `조금도 추측하지 말라`는 제한을 풀고, 원문에 없는 요소·모순·갈등 표현·친구 모드 연애 신호·보호 의도의 모호함까지 무조건 차단하지 말고 UI 주의사항으로 보여 달라고 했다.
- 확인한 내용: 기존 검증은 안전했지만 창의적 출력 대부분을 `EXPLICIT_INTENT_AMBIGUOUS`나 `UNSUPPORTED_PERSONAL_DEVICE`로 거절해 7단계 성공률을 낮췄다. 반대로 방·참여자 혼합이나 잘못된 근거 ID 같은 구조적 오류까지 풀면 안 됐다.
- 바뀐 내용: 6·7단계의 창의적 스타일 규칙은 결과를 반환하면서 경고를 표시하는 권고형 검증으로 전환했다. 출력 구조, 정확히 세 답장, 방·참여자 범위, 암호화·인증과 개인 컨텍스트 ID 검증은 계속 강제했다.
- 결과: 높은 단계가 창의성을 이유로 반복 500에 빠지는 일이 줄고, 사용자는 위험을 읽은 뒤 결과를 직접 선택·수정할 수 있게 됐다.

### 4. 추가 설명 뒤 재생성 흐름을 다시 다듬었다

- 내가 요청하거나 한 행동: `한 가지만 확인할게요`가 왜 나타나는지, 설명을 입력해도 다시 만들기가 실패하는 이유를 반복해서 확인했다.
- 확인한 내용: 대명사·생략 사건 때문에 정말 불명확한 경우와, 이미 사용자가 충분한 상황·의도를 적은 경우를 더 잘 구분해야 했다. 최근 턴의 대명사를 조사·어미까지 포함해 인식할 필요도 있었다.
- 바뀐 내용: `걔는`, `그거야`, `그것을` 같은 한국어 형태를 감지하고 `그래서` 같은 오탐을 제외했다. 사용자의 추가 설명을 최신 현재 맥락에 넣어 한 번의 질문 뒤 재시도하도록 했다.
- 결과: 불필요한 409 질문은 줄고, 정말 부족한 경우에는 질문 하나로 복구할 수 있게 됐다.

### 5. GitHub 저장소와 브랜치 작업을 정리했다

- 내가 요청하거나 한 행동: 로컬 변경을 GitHub 저장소에 올리고 어디에서 확인하는지 물었으며, 기능 브랜치 작업이 `main`에 병합됐는지도 확인했다.
- 확인한 내용: clone 직후 상위 폴더에서는 Git 명령이 동작하지 않았고, 기능 브랜치에만 있는 커밋은 Render의 `main` 배포에 반영되지 않았다.
- 바뀐 내용: 원격 저장소를 `https://github.com/gimghoon/2026_summer_mks.git`로 연결하고, 기능은 `codex/` 브랜치에서 작업한 뒤 검토·병합하는 흐름을 사용했다. 개인 컨텍스트 완화 브랜치까지 최종적으로 `main`에 병합했다.
- 결과: GitHub의 `main`이 누적 제품 기능의 기준이 되고 Render가 같은 기준을 배포할 수 있게 됐다.

### 6. Render 배포를 단계별로 시작했다

- 내가 요청하거나 한 행동: 이 서비스를 실제로 배포할 수 있는지 묻고 단계별 안내에 따라 Render 웹 서비스와 PostgreSQL을 만들었다.
- 확인한 내용: 배포 환경에는 로컬 `.env.local`과 로컬 PostgreSQL이 없으므로 모든 비밀값과 DB 연결을 Render에 별도로 등록해야 했다. 배포 서버가 있으므로 사용자가 매번 로컬 `pnpm dev`를 켤 필요는 없었다.
- 바뀐 내용: Render에 PostgreSQL과 웹 서비스를 연결하고 `DATABASE_URL`, 비밀번호 해시, 세션·암호화 키, OpenAI 키와 모델 이름을 비밀 환경변수로 등록하는 절차를 정했다. 프로덕션 시작 명령으로 `pnpm start`를 사용했다.
- 결과: 공개 서비스 주소 `https://two026-summer-mks.onrender.com`에서 앱을 실행할 수 있는 배포 기반이 마련됐다.

### 7. Render의 잘못된 DB URL과 없는 테이블을 해결했다

- 내가 요청하거나 한 행동: 배포 로그인 때 `DATABASE_URL Invalid input`과 이후 `relation "rooms" does not exist` 로그를 공유했다.
- 확인한 내용: 첫 오류는 PostgreSQL URL 값이 유효하지 않았고, 두 번째 오류는 연결은 됐지만 Drizzle 마이그레이션이 적용되지 않았다는 뜻이었다.
- 바뀐 내용: Render PostgreSQL의 정확한 내부 연결 URL을 환경변수에 넣고, 배포 과정에 `pnpm exec drizzle-kit migrate`를 포함했다. `vector`와 `pgcrypto` 확장 및 테이블 생성을 배포 전에 확인하도록 했다.
- 결과: 앱이 배포 DB에 연결하고 방 목록을 조회할 수 있게 됐다.

### 8. Render의 `corepack enable` 빌드 실패를 고쳤다

- 내가 요청하거나 한 행동: 배포 로그의 `EROFS: read-only file system, unlink '/usr/bin/pnpm'` 오류를 공유했다.
- 확인한 내용: Render 이미지의 `/usr/bin`은 읽기 전용인데 `corepack enable`이 기존 pnpm 링크를 교체하려고 했다.
- 바뀐 내용: 빌드 명령에서 무조건적인 `corepack enable`을 제거하고, 환경에 제공된 pnpm과 저장소의 lockfile·`packageManager` 설정을 사용하도록 했다. 설치 → 마이그레이션 → 빌드 순서를 유지했다.
- 결과: 읽기 전용 시스템 경로를 수정하지 않고 프로덕션 빌드를 완료할 수 있게 됐다.

### 9. 배포 로그인 뒤 화면이 그대로인 문제를 고쳤다

- 내가 요청하거나 한 행동: 올바른 비밀번호를 입력하면 처음에는 `/login` 화면에 그대로 있지만, 뒤로 갔다 방 열기를 누르면 로그인된 상태가 되는 현상을 설명했다. 네트워크 응답의 `Location`이 `https://localhost:10000/`인 것도 확인했다.
- 확인한 내용: 세션 쿠키와 303은 성공했지만, Render 내부 요청 URL로 만든 절대 이동 주소 때문에 브라우저가 잘못된 호스트로 이동하려 했다.
- 바뀐 내용: 로그인 성공 응답의 이동 주소를 절대 URL이 아닌 상대 경로 `/rooms`로 변경했다. 세션 통합 테스트도 `/rooms`를 기대하도록 수정하고, 프록시 헤더 보존 지침을 운영 문서에 반영했다.
- 결과: 로그인 성공 직후 배포 도메인의 방 목록으로 정상 이동하게 됐다.

### 10. 실제 카카오톡 CSV 내보내기를 지원했다

- 내가 요청하거나 한 행동: 카카오톡에서 실제로 추출된 `.csv` 파일을 보여주고 이 형식에 맞춰 달라고 했다.
- 확인한 내용: 초기 파서는 TXT 구조만 가정해 CSV의 헤더, 인용부호, 쉼표와 여러 줄 본문을 정확히 읽지 못했다. 파싱 결과가 0턴이면 분석이 `hierarchy_validation`에서 실패할 수 있었다.
- 바뀐 내용: 인코딩과 헤더를 판별하는 CSV 파서, 따옴표·쉼표·멀티라인 처리와 TXT/CSV 자동 선택을 추가했다. 업로드 UI와 검수 결과도 두 형식을 구분하도록 했다.
- 결과: 사용자가 카카오톡에서 실제로 받은 CSV 내보내기를 별도 변환 없이 업로드할 수 있게 됐다.

### 11. GitHub 잔디가 보이지 않는 원인을 확인했다

- 내가 요청하거나 한 행동: 커밋이 GitHub에는 올라가는데 기여 그래프의 잔디가 생기지 않거나 병합 뒤 없어 보이는 이유를 물었다.
- 확인한 내용: 잔디는 push 횟수가 아니라 기본 브랜치에 포함된 커밋의 작성자 이메일이 GitHub 계정의 확인된 이메일과 연결되는지를 기준으로 계산한다. 설정을 바꿔도 과거 커밋 작성자 정보는 자동 변경되지 않는다.
- 바뀐 내용: 저장소의 `user.name`과 `user.email`을 GitHub 표시 이름과 확인된 이메일 또는 GitHub noreply 이메일로 설정했다. 기능 브랜치가 `main`에 병합됐는지도 확인했다.
- 결과: 이후 조건을 만족하는 새 커밋은 기여 그래프에 반영될 수 있게 됐다. GitHub 처리에는 시간이 걸릴 수 있으며 과거 커밋은 별도 이력 변경 없이는 그대로 남는다.

### 12. 답장에 개인 컨텍스트 근거를 보여 달라고 했다

- 내가 요청하거나 한 행동: 6·7단계에서는 추측 제한을 완화하되, 각 답장이 전달 의도뿐 아니라 프로필의 어떤 개인 컨텍스트를 근거로 했는지 표시해 달라고 했다.
- 확인한 내용: 일반 답장도 선택한 참여자의 프로필을 참고했지만, 사용자는 어떤 사실이 실제 근거가 됐는지 확인할 수 없었다.
- 바뀐 내용: 답장 후보 구조에 퍼스널 컨텍스트 근거 요약과 경고를 추가하고 결과 카드에 표시했다. 근거 원문과 내부 ID는 암호화 저장하고 사용자에게는 이해 가능한 요약만 보여주도록 했다.
- 결과: 답장이 특정 친구의 프로필을 어떻게 활용했는지 사용자가 결과 화면에서 검토할 수 있게 됐다.

### 13. 프로필 개인 컨텍스트를 모든 답장에 반드시 쓰는 모드를 요청했다

- 내가 요청하거나 한 행동: 선택한 인물의 프로필에 저장된 개인 컨텍스트를 무조건 인용해 답장하는 별도 모드를 추가해 달라고 했다.
- 확인한 내용: 일반 모드는 프로필을 참고하지만 세 답장 모두에 특정 사실이 드러난다고 보장하지 않았다. 확정된 사용자 사실과 AI 추정의 신뢰도도 구분해야 했다.
- 바뀐 내용: `개인 컨텍스트 필수 반영` 체크박스와 저장 설정을 추가했다. 각 후보가 유효한 프로필 사실 ID를 하나 이상 선택하도록 하고, 사용자 수정 → 사용자 확인 → 잠긴 사실 → AI 추정 순으로 근거를 선택했다. AI 추정만 있으면 경고하고, 사용할 사실이 없으면 프로필 확인 링크와 409를 반환했다.
- 결과: 필수 모드에서는 답장 세 개 각각이 선택한 참여자의 저장된 사실을 근거로 갖는다는 구조적 보장이 생겼다.

### 14. `PERSONAL_CONTEXT_NOT_REFLECTED` 반복 실패 원인을 확인했다

- 내가 요청하거나 한 행동: 필수 모드를 켰을 때 `ReplyGenerationValidationError:PERSONAL_CONTEXT_NOT_REFLECTED`가 반복된다며, 프로필을 보고 판단하는 것이 맞는지 확인했다.
- 확인한 내용: 시스템은 실제로 선택 참여자의 프로필을 불러오고 있었지만, 선택한 사실이 답장 문장에 자연스럽게 반영됐는지를 별도 의미 모델이 너무 엄격하게 판정했다. 근거 ID는 올바른데 표현 방식이 달라 실패하는 경우가 있었다.
- 바뀐 내용: 프로필 선택 경로와 우선순위를 다시 검증하고, 실패 로그가 원문 없이 규칙명만 남도록 유지했다. 의미 검증과 구조적 근거 검증을 분리했다.
- 결과: 문제의 원인이 프로필 미조회가 아니라 자연스러운 반영을 판정하는 강도라는 점이 분명해졌다.

### 15. 개인 컨텍스트 확인 조건을 단순 완화했다

- 내가 요청하거나 한 행동: 개인 컨텍스트가 자연스럽게 반영됐는지 확인하는 강도를 줄이고 조건을 느슨하게 하자고 했으며, 여러 방식 중 `단순완화`를 선택했다.
- 확인한 내용: 유효한 프로필 사실을 골랐다는 조건은 여전히 필요하지만, 의미 검사 하나 때문에 모델을 재호출하거나 전체 요청을 500으로 실패시킬 필요는 없었다.
- 바뀐 내용: 유효한 선택 사실 ID 검증은 계속 강제하고, 의미적 반영 실패는 재시도·차단 대신 `개인 컨텍스트가 약하게 반영됐을 수 있어요.` 경고로 바꿨다. 검증기를 사용할 수 없을 때도 별도 안내를 표시하도록 했다.
- 결과: 필수 모드의 근거 보장은 유지하면서 표현이 자연스러운지에 대한 애매한 판정 때문에 답장을 받지 못하는 문제를 줄였다.

### 16. 기능 브랜치를 `main`에 병합하고 현재 기준을 정리했다

- 내가 요청하거나 한 행동: 개인 컨텍스트 완화 작업이 별도 브랜치에만 있는지, 나머지 브랜치도 `main`에 병합해야 하는지 확인한 뒤 병합을 완료했다.
- 확인한 내용: Render와 GitHub 기본 화면은 `main`을 기준으로 하므로 기능 브랜치 커밋만 push해서는 실제 서비스가 바뀌지 않는다.
- 바뀐 내용: 관련 기능 브랜치와 수정 커밋을 `main`에 병합하고 원격 저장소에 반영했다.
- 결과: 현재 `main`에는 TXT/CSV 가져오기, 재개 가능한 분석, 프로필 교정, 답장 3개, 1~7단계, 권고형 창의 검증과 개인 컨텍스트 필수·완화 기능이 함께 포함돼 있다.

### 17. 현재 운영 상태와 남은 주의점을 확인했다

- 내가 요청하거나 한 행동: 선택한 인물의 `답장` 링크가 실제로 그 인물의 개인 컨텍스트를 사용하는지 확인하고, 지금까지의 설계와 수정 과정을 정리해 달라고 했다.
- 확인한 내용: 링크는 방 ID와 참여자 ID를 함께 전달하고 서버는 같은 방의 선택 참여자 프로필만 불러온다. 일반 모드는 프로필을 참고하고, 필수 모드는 모든 후보에 선택 근거 ID를 요구한다. 다만 의미적 자연스러움은 현재 경고형 검사다.
- 바뀐 내용: 현재 동작과 한계를 문서로 명시했다. `.env.local`, 실제 대화, 비밀번호와 API 키는 Git에 올리지 않고, 배포 전 단위·통합·타입·빌드와 전용 PostgreSQL 삭제 검증을 수행하도록 정리했다.
- 결과: 서비스는 개인용 MVP로 사용할 수 있지만, 6·7단계와 개인 컨텍스트 경고가 있는 답장은 사용자가 읽고 수정한 뒤 보내야 한다. 공개 다중 사용자 서비스로 확장하려면 계정 격리, 운영 모니터링, 데이터 보존 정책과 추가 보안 검토가 필요하다.
