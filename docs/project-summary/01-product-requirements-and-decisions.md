# 1편 — 아이디어 구체화와 초기 설계

## 이 문서가 다루는 시기

이 문서는 서비스를 처음 떠올린 순간부터 개인용 MVP의 기능과 기본 설계를 확정하기까지의 과정을 시간순으로 기록한다. 실제 카카오톡 원문과 비밀번호·API 키 같은 민감정보는 포함하지 않는다.

### 1. 친구별 맥락을 이해하는 답장 추천기를 제안했다

- 내가 요청하거나 한 행동: 남자 동성 친구들과 나눈 카카오톡 대화를 프로그램에 주면, 친구 각각의 특징과 대화 맥락을 파악한 뒤 현재 대화에 맞는 메시지를 추천하는 프로그램을 만들고 싶다고 설명했다.
- 확인한 내용: 단순히 한 문장을 다른 말투로 바꾸는 도구가 아니라, 대화방별 장기 기억과 사람별 프로필이 필요한 서비스였다. 현재 대화만 보면 이해할 수 없는 농담, 반복 사건과 관계 특성도 답장에 영향을 줘야 했다.
- 바뀐 내용: 제품의 중심을 `대화방 전체 분석 → 참여자별 장기 맥락 → 현재 대화 답장 추천` 흐름으로 정했다.
- 결과: 서비스의 핵심 목표가 일반 문장 변환기가 아니라 개인 관계 맥락을 사용하는 카카오톡 답장 추천기로 확정됐다.

### 2. 말투를 고정된 `여자어` 콘셉트로 정했다

- 내가 요청하거나 한 행동: 성별 중립적인 스타일이 아니라 반드시 여성 친구처럼 말하는 고정된 성별 말투가 제품 콘셉트라고 분명히 했다.
- 확인한 내용: 이 스타일을 모든 여성의 보편적 특성으로 주장하면 안 되지만, 사용자가 의도적으로 선택한 창작·메신저 스타일 규칙으로 구현할 수 있었다.
- 바뀐 내용: 제품 안에서 `여자어`를 한국 20대 여성의 사적인 메신저 말투를 참고한 선택형 스타일 콘셉트로 정의했다.
- 결과: 이후 답장 정책, 예시와 UI 설명은 이 고정 콘셉트를 중심으로 설계하게 됐다.

### 3. 한국 20대 여성의 간접적인 감정 표현을 강조했다

- 내가 요청하거나 한 행동: 한국 여성을 기준으로 규칙을 조사하고, 특히 여자들이 감정을 직접 말하지 않고 돌려 표현하는 특징을 강조해 달라고 했다. 남녀가 싸운 상황에서 주고받은 메시지에서도 힌트를 얻고 싶다고 했다.
- 확인한 내용: 단순히 이모지나 어미를 붙이는 것으로는 원하는 느낌이 나오지 않았다. 감정, 관계 목표와 상대에게 기대하는 행동을 먼저 정한 뒤 상황 묘사·완곡한 질문·여운으로 변환해야 했다.
- 바뀐 내용: 스타일 변환 순서를 `감정 파악 → 관계 목표 선택 → 간접 표현 장치 적용 → 핵심 의도 확인`으로 설계했다. 실제 사적 대화를 무단 수집하지 않고 연구 자료, 허가된 예시와 합성 예문만 사용하기로 했다.
- 결과: 제품의 `여자어`는 장식적인 말끝 변화가 아니라 감정을 우회적으로 전달하는 규칙 기반 엔진으로 구체화됐다.

### 4. 전체 파일과 현재 대화 붙여넣기를 모두 지원하기로 했다

- 내가 요청하거나 한 행동: 카카오톡에서 내보낸 파일 업로드와 현재 대화 붙여넣기 두 방식을 모두 지원하겠다고 선택했다.
- 확인한 내용: 전체 파일은 친구별 장기 기억을 만드는 데 적합하고, 붙여넣은 최근 대화는 지금 답해야 하는 작은 맥락을 전달하는 데 적합했다.
- 바뀐 내용: 초기 입력을 `카카오톡 .txt 전체 내보내기`와 `현재 대화 복사·붙여넣기`로 분리했다. 전체 파일은 방별 저장 지식을 만들고, 현재 입력은 답장 요청 때만 사용하도록 했다.
- 결과: 매번 전체 대화를 모델에 보내지 않고도 장기 맥락과 현재 맥락을 결합할 수 있는 구조가 정해졌다.

### 5. 대화방마다 독립된 맥락을 만들기로 했다

- 내가 요청하거나 한 행동: 업로드한 파일의 대화방별로 서로 다른 맥락을 만들어 달라고 했다.
- 확인한 내용: 같은 별명이나 사건이 여러 방에서 다른 의미를 가질 수 있고, 다른 방의 사람이나 이야기가 섞이면 개인화 답장이 오히려 위험해질 수 있었다.
- 바뀐 내용: 모든 메시지, 참여자, 청크, 기억, 프로필과 답장 요청을 대화방 범위로 묶기로 했다. 검색도 먼저 방을 강제 필터링한 뒤 관련도를 계산하도록 설계했다.
- 결과: 각 대화방이 하나의 독립된 기억 공간이 되고, 선택한 방 밖의 원문을 답장에 사용하지 않는 원칙이 생겼다.

### 6. 전체 대화로 친구 프로필을 먼저 만들고 사용자가 고치기로 했다

- 내가 요청하거나 한 행동: 처음 전체 대화를 주면 AI가 친구별 말투, 대화 특징과 성격 같은 것을 먼저 파악하고, 헷갈리는 부분은 사용자가 수정하는 방식이 좋겠다고 했다.
- 확인한 내용: AI의 성격 판단은 확정 사실이 아니라 관찰된 추정이어야 했다. 사용자가 확인하거나 수정한 내용은 이후 재분석에서도 보존돼야 했다.
- 바뀐 내용: 참여자별로 관계, 말투, 대화 역할, 관심사, 갈등·화해 방식, 별명, 반복 사건, 근거, 확신도와 출처를 저장하는 프로필을 설계했다. 사용자 수정은 AI 추정보다 높은 우선순위를 갖고 잠글 수 있게 했다.
- 결과: 답장 생성 전에 친구별 분석을 검수하고 개인 지식을 쌓을 수 있는 프로필 개념이 확정됐다.

### 7. 프로필은 직접 편집과 대화형 교정을 모두 지원하기로 했다

- 내가 요청하거나 한 행동: 프로필을 고치는 두 방식을 모두 지원하겠다고 선택했다.
- 확인한 내용: 단순한 값은 폼에서 직접 고치는 편이 빠르고, `친한 사람에게만 저렇게 말해` 같은 조건부 설명은 자연어가 더 편했다.
- 바뀐 내용: 프로필 항목 직접 편집과 AI 교정 채팅을 함께 설계했다. 교정 채팅은 사용자의 문장을 즉시 덮어쓰지 않고 어떤 사실로 저장할지 제안한 뒤 확인받도록 했다.
- 결과: 사용자가 AI 분석을 수동 데이터 입력처럼 다루지 않고도 자연스럽게 교정할 수 있게 됐다.

### 8. 현재 맥락은 최근 20턴에서 시작해 필요할 때 확장하기로 했다

- 내가 요청하거나 한 행동: 현재 대화를 최근 20개의 대화 덩어리로 보고, 의미 없는 메시지가 많을 때 조금씩 범위를 늘리는 것이 좋은지 물었다. 동시에 현재 상황은 사용자가 판단해 직접 알려주는 것이 좋아 보인다고 했다.
- 확인한 내용: 고정된 20턴만 사용하면 `그거`, `그때`, 단답과 웃음 표현이 많은 대화를 이해하지 못할 수 있었다. 반대로 처음부터 전체 대화를 보내면 느리고 사생활 노출 범위가 커졌다.
- 바뀐 내용: 현재 맥락을 `20 → 40 → 80 → 현재 대화 덩어리 전체`로 확장하도록 설계했다. 끝까지 부족하면 질문 하나만 하고, 사용자가 입력한 상황과 의도는 자동 추정보다 우선하도록 했다.
- 결과: 최소 원문으로 시작하면서도 애매한 대화를 복구할 수 있는 적응형 맥락 방식이 정해졌다.

### 9. 친구 모드와 여자친구 모드를 분리했다

- 내가 요청하거나 한 행동: 답장 관계 유형으로 여성 친구와 여자친구 두 방식을 모두 지원하기로 했다.
- 확인한 내용: 여성 친구에게 연애·질투·소유 표현이 들어가면 관계를 잘못 해석할 수 있고, 여자친구 답장에서 애정 신호를 모두 금지하면 원하는 표현이 나오지 않았다.
- 바뀐 내용: 여성 친구 모드는 친근함·공감·완곡함을 사용하되 연애 신호를 억제하고, 여자친구 모드는 확인된 관계에서 애정·서운함·질투·기대 표현을 허용하도록 했다.
- 결과: 동일한 현재 대화라도 사용자가 선택한 관계에 따라 다른 스타일 정책을 적용하게 됐다.

### 10. 돌려 말하기 강도를 사용자가 조절하기로 했다

- 내가 요청하거나 한 행동: 답장을 만드는 우회 강도를 정하고 설정에서 사용자가 수정할 수 있게 해 달라고 했다.
- 확인한 내용: 한 가지 강도로 고정하면 평소 대화와 갈등 상황 모두에 맞추기 어려웠다. 기본 선호와 이번 요청의 목적도 다를 수 있었다.
- 바뀐 내용: 초기에는 1~5단계를 설계하고 3단계를 기본값으로 정했다. 설정에는 기본 강도를 저장하고, 답장 화면에서는 이번 요청에만 임시 변경할 수 있게 했다.
- 결과: 사용자가 직접적인 답장부터 상당히 우회적인 답장까지 상황에 맞춰 선택할 수 있게 됐다.

### 11. 같은 강도에서 전략이 다른 답장 세 개를 요청했다

- 내가 요청하거나 한 행동: 한 답만 주는 대신 여러 선택지를 받을 수 있는 방향을 승인했다.
- 확인한 내용: 단순히 비슷한 문장 세 개를 만들면 선택의 의미가 없었다. 같은 강도를 지키면서 관계 유지, 감정 신호와 요구 전달의 우선순위를 달리해야 했다.
- 바뀐 내용: 답장 전략을 `관계를 부드럽게 유지`, `감정을 자연스럽게 눈치채게 함`, `요구나 감정을 조금 더 분명히 전달`의 세 가지로 고정했다. 각 결과에 전달 의도와 주의점을 붙이기로 했다.
- 결과: 사용자는 같은 상황에서도 서로 다른 목적을 가진 정확히 세 개의 답장을 비교할 수 있게 됐다.

### 12. 중요한 의도는 처음에는 강하게 보호하기로 했다

- 내가 요청하거나 한 행동: 우회 표현을 강하게 만들되 실제 의미가 완전히 사라지지 않는 제품을 원했다.
- 확인한 내용: 송금, 동의, 안전, 거절과 중요한 약속은 너무 돌려 말하면 실제 결정이 바뀌거나 오해될 수 있었다. 원문에 없는 사람·금액·날짜를 만들어내는 문제도 막아야 했다.
- 바뀐 내용: 초기 정책에서는 명백한 사실 발명, 구조화된 사실과의 모순, 강요·협박·갈등 확대, 친구 모드의 연애 신호와 보호 의도의 모호화를 차단하도록 했다.
- 결과: 창의성보다 사실 보존과 관계 안전을 우선하는 첫 검증 정책이 만들어졌다. 이 정책은 이후 높은 우회 단계에서 사용자의 요청에 따라 일부가 권고형으로 바뀐다.

### 13. 개인용 MVP 범위를 최종 확정했다

- 내가 요청하거나 한 행동: 일단 개인용으로 만들자고 결정하고 설계와 개발 진행을 승인했다.
- 확인한 내용: 공개 서비스에 필요한 회원 관리, 결제, 관리자 기능보다 개인 대화 보호, 분석 교정과 답장 품질이 우선이었다.
- 바뀐 내용: 단일 사용자 로그인, 암호화 저장, 방 삭제, 모바일 중심 UI, 프로필 검수와 수동 복사 전송을 MVP 범위로 확정했다. 카카오톡 직접 연동, 자동 발송, 다중 사용자와 미세조정은 제외했다.
- 결과: 2026년 8월 7일 초기 제품 설계와 구현 계획이 승인됐고, 다음 단계부터 실제 MVP 개발이 시작됐다.
