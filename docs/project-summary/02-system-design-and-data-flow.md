# 2편 — MVP 개발과 로컬 테스트

## 이 문서가 다루는 시기

이 문서는 초기 설계 승인 뒤 실제 MVP를 만들기 시작한 시점부터, 사용자가 로컬에서 카카오톡 파일 분석과 답장 생성을 시험하며 주요 장애를 해결한 시점까지를 시간순으로 기록한다.

### 1. 테스트 중심 절차보다 MVP 구현을 먼저 요청했다

- 내가 요청하거나 한 행동: 긴 TDD 절차를 빼고 우선 사용할 수 있는 MVP부터 개발해 달라고 했다.
- 확인한 내용: 화면만 있는 데모가 아니라 로그인, 데이터 저장, 가져오기, 분석, 프로필과 답장까지 이어지는 최소한의 실제 흐름이 필요했다.
- 바뀐 내용: 앱 골격과 데이터 구조부터 순서대로 만들고, 각 기능이 연결될 때 필요한 수준의 단위·통합 테스트와 빌드 검증을 함께 진행했다.
- 결과: 2026년 8월 7일부터 기능별 구현이 시작됐고, 이후 변경을 안전하게 받을 수 있는 기본 코드베이스가 만들어졌다.

### 2. 앱 골격과 암호화 데이터 기반을 만들었다

- 내가 요청하거나 한 행동: 개인 대화를 다루는 실제 웹앱으로 진행하도록 승인했다.
- 확인한 내용: 방 제목, 참여자 이름, 메시지, 요약, 프로필과 답장은 모두 민감정보였다. 데이터베이스와 로그에 평문이 남으면 안 됐다.
- 바뀐 내용: Next.js·React·TypeScript 앱, PostgreSQL·Drizzle 스키마, 인증 암호화 JSON 저장소와 안전한 구조화 로그를 구현했다. 메시지부터 답장 후보까지 방 삭제 시 함께 지워지는 관계를 설계했다.
- 결과: 이후 기능은 평문을 직접 저장하지 않고 암호화 저장소와 방 범위 인터페이스를 통해 데이터를 다루게 됐다.

### 3. 단일 사용자 로그인과 요청 제한을 만들었다

- 내가 요청하거나 한 행동: 개인용으로 혼자 사용할 수 있는 로그인 기능을 원했다.
- 확인한 내용: 공개 회원가입은 필요 없었지만, 비밀번호 평문 저장과 약한 세션 키는 피해야 했다. 로그인 전에 큰 요청 본문을 읽는 것도 방어해야 했다.
- 바뀐 내용: Argon2id 비밀번호 해시 비교, 12시간 서명 세션 쿠키, 32바이트 base64 서명 키 검증과 로그인 요청 크기 제한을 구현했다.
- 결과: 인증되지 않은 API 요청은 401, 브라우저 페이지는 로그인 화면으로 이동하는 단일 사용자 보호 경계가 생겼다.

### 4. 카카오톡 TXT 가져오기와 같은 방 추가 업로드를 구현했다

- 내가 요청하거나 한 행동: 카카오톡에서 내보낸 전체 파일로 방과 친구들을 분석하고, 나중에 같은 방의 새 대화도 추가하고 싶다고 했다.
- 확인한 내용: 여러 줄 메시지, 본문 없는 이벤트와 같은 내용의 재업로드를 구분해야 했다. 같은 사람이 같은 시각에 같은 문장을 실제로 반복할 수도 있었다.
- 바뀐 내용: TXT 파서, 메시지 정규화, 결정적 발생 순번이 포함된 지문, 방·참여자 생성과 중복 제거를 구현했다. 기존 대화방 ID를 선택해 증분 가져오기를 할 수 있게 했다.
- 결과: 전체 파일 재업로드는 중복을 만들지 않으면서, 실제 반복 메시지와 새 메시지는 보존할 수 있게 됐다.

### 5. 모델 연결과 계층형 기억을 구현했다

- 내가 요청하거나 한 행동: 전체 대화를 먼저 분석해 방의 맥락과 친구별 프로필을 만들어 달라고 했다.
- 확인한 내용: 한 번의 요약만 저장하면 근거를 추적하거나 사용자 수정과 AI 추정을 구분하기 어려웠다. 분석 실패 뒤 재시도할 때 이전 결과를 잘못 덮어쓸 위험도 있었다.
- 바뀐 내용: 분석용 모델과 답장용 모델 목적을 분리하고, 청크 → 주제·사건 → 방 기억 → 프로필 사실 계층을 구현했다. 프로필에는 근거, 확신도, 출처, 잠금과 수정 이력을 저장했다.
- 결과: 사용자 편집과 확인 사실을 우선하면서도 새 대화를 재분석할 수 있는 장기 기억 기반이 생겼다.

### 6. 프로필 직접 수정과 확인형 교정 채팅을 연결했다

- 내가 요청하거나 한 행동: AI가 잘못 파악한 친구 특징을 직접 고치거나 자연어로 설명할 수 있어야 한다고 했다.
- 확인한 내용: 자연어 교정을 즉시 저장하면 사용자의 의도와 다른 필드가 바뀔 수 있었다. 다른 대화방 참여자의 프로필을 잘못 수정하는 것도 막아야 했다.
- 바뀐 내용: 방·참여자 범위를 검사하는 프로필 조회·수정 API, 직접 편집 UI와 `수정 제안 → 사용자 확인 → 저장` 교정 채팅을 구현했다.
- 결과: AI 분석을 사용자가 검수하고 수정한 사실을 잠글 수 있게 됐으며, 재분석에서도 사용자 지식이 보존됐다.

### 7. 적응형 현재 맥락과 관련 과거 검색을 구현했다

- 내가 요청하거나 한 행동: 최근 20개 대화가 의미 없으면 조금씩 확장하고, 친구별 과거 맥락도 답장에 반영해 달라고 했다.
- 확인한 내용: 단순 벡터 유사도만 사용하면 다른 사람의 비슷한 사건이 섞일 수 있었다. `걔는`, `그거야`, `그것을`처럼 조사가 붙은 대명사도 애매함 신호로 인식해야 했다.
- 바뀐 내용: 20→40→80→전체 확장기와 한국어 대명사 검사를 구현했다. 검색은 방을 먼저 고정하고 참여자, 주제, 사건, 별명과 관계 신호를 함께 사용하며 상위 소수 청크만 복호화하도록 했다.
- 결과: 전체 원문을 매번 보내지 않으면서도 선택한 친구와 관련된 현재·과거 맥락을 답장에 결합할 수 있게 됐다.

### 8. 답장 세 개와 모바일 작업 화면을 완성했다

- 내가 요청하거나 한 행동: 친구·여자친구 모드와 우회 강도를 반영한 답장 세 개를 모바일에서 보고 수정·복사하고 싶다고 했다.
- 확인한 내용: 관계 선택, 기본 강도와 수정된 답장이 UI에만 있고 실제 요청·복사 결과에 반영되지 않는 초기 연결 문제가 있었다. 분석이 준비되지 않았는데도 프로필과 답장 링크가 열리면 안 됐다.
- 바뀐 내용: 정확히 세 전략을 반환하는 답장 서비스, 관계·강도 API 연결, 수정 상태를 유지하는 결과 카드와 복사 피드백을 구현했다. 방의 실제 분석 준비 상태가 완료일 때만 프로필과 답장을 열도록 했다.
- 결과: 로그인 → 업로드 → 분석 → 프로필 검수 → 답장 생성 → 수정·복사의 모바일 MVP 흐름이 연결됐다.

### 9. GitHub에서 코드를 받아 로컬 실행을 시작했다

- 내가 요청하거나 한 행동: GitHub 저장소를 clone한 뒤 다음에 무엇을 해야 하는지 물었고, 터미널에서 설치·환경설정 명령을 실행했다.
- 확인한 내용: 처음에는 clone한 상위 폴더에서 `branch`, `pnpm install`과 `.env.example` 복사를 실행해 명령 또는 파일을 찾지 못했다. `branch`는 셸 명령이 아니라 `git branch`였고, 실제 앱은 한 단계 안쪽 프로젝트 루트에 있었다.
- 바뀐 내용: `pwd`, `ls`, `git status`로 `package.json`이 있는 `/Users/gimghoon/developer/codexP1/2026_summer_mks`를 확인하고, 그 위치에서 Node·pnpm 설치와 환경설정을 진행했다.
- 결과: 잘못된 폴더 문제를 해결하고 실제 앱 의존성을 설치할 수 있게 됐다.

### 10. PostgreSQL을 설치하고 로컬 DB를 준비했다

- 내가 요청하거나 한 행동: Docker와 `psql`이 없다는 결과를 공유한 뒤 Homebrew PostgreSQL을 설치하고 상태를 확인했다.
- 확인한 내용: 애플리케이션은 PostgreSQL과 `pgvector` 스키마를 전제로 했기 때문에 DB 없이 방 목록과 분석을 사용할 수 없었다.
- 바뀐 내용: PostgreSQL 17을 실행하고 `pg_isready`가 `/tmp:5432`에서 접속을 받는 것을 확인했다. 로컬 데이터베이스 URL을 설정하고 Drizzle 마이그레이션을 적용했다.
- 결과: 로컬 앱이 방·메시지·분석 결과를 실제 DB에 저장할 준비가 끝났다.

### 11. 로그인 `Unauthorized`를 단계적으로 점검했다

- 내가 요청하거나 한 행동: 올바른 비밀번호를 입력했다고 생각했는데 계속 로그인되지 않아 환경파일을 다시 고쳐야 하는지, 해시에 따옴표와 `$`를 어떻게 다뤄야 하는지 물었다.
- 확인한 내용: 앱은 평문이 아니라 Argon2 해시를 요구했다. 해시의 `$`가 셸에서 해석되거나, 비밀번호 입력 명령 자체에 평문을 써 넣는 방식으로 오해할 수 있었다. 환경변수를 바꾼 뒤 서버를 재시작하지 않으면 이전 값이 남았다.
- 바뀐 내용: `read -s` 프롬프트가 뜬 뒤 비밀번호를 보이지 않게 입력해 해시를 만들고, 생성된 전체 해시를 `.env.local`의 `APP_PASSWORD_HASH`에 저장하는 절차로 정리했다. 세션 키 형식도 함께 확인했다.
- 결과: 해시 생성 명령 안에 비밀번호를 직접 적지 않고도 로컬 로그인을 검증할 수 있게 됐다.

### 12. 실제 카카오톡 파일을 올려 첫 분석을 시험했다

- 내가 요청하거나 한 행동: 다운로드한 카카오톡 대화 파일이 테스트 데이터로 적합한지 확인하고 실제로 업로드했다.
- 확인한 내용: 파일 가져오기 POST는 201로 성공했고 분석 POST도 처음에는 200을 반환했지만, 화면에는 `검수가 필요해요`가 남거나 진행이 45%에서 멈췄다. 당시 상태 표시가 실제 완료 청크보다 화면 단계에 가까웠다.
- 바뀐 내용: 방 상세 화면에서 저장된 청크와 방 기억을 읽어 실제 분석 준비 여부를 계산하고, 미파싱 줄 검수와 분석 재시도를 구분하도록 했다.
- 결과: 업로드 성공과 분석 완료를 같은 상태로 취급하지 않게 됐고, 사용자는 어느 단계가 남았는지 확인할 수 있게 됐다.

### 13. 약 1,000개 메시지 분석이 수분 뒤 503으로 실패했다

- 내가 요청하거나 한 행동: 분석 시간이 얼마나 걸리는지 물었고, `POST /analysis 503 in 228873ms`와 반복되는 503 로그를 공유했다. 문제를 해결할 기능을 추가하자고 승인했다.
- 확인한 내용: 긴 대화를 한 번의 큰 청크와 긴 HTTP 요청으로 분석하면 모델 일시 오류 한 번이 전체 방 실패로 이어졌다. 같은 PostgreSQL 클라이언트에 쿼리가 겹치는 경고도 보였다.
- 바뀐 내용: 청크를 최대 20턴으로 제한하되 30분·날짜·주제 경계를 유지했다. 청크별 진행 상태, 완료 결과 보존, GET 상태 조회, 실패 지점 재개, 제공자 일시 오류 재시도와 advisory lock을 추가했다.
- 결과: 긴 분석이 중간에 실패해도 이미 완료한 청크를 다시 결제·분석하지 않고 다음 시도에서 이어갈 수 있게 됐다. 진행률도 완료 청크 수를 기준으로 표시됐다.

### 14. 분석은 끝났지만 답장 생성이 500으로 실패했다

- 내가 요청하거나 한 행동: 분석 완료 뒤 답장 버튼을 눌렀지만 `ReplyGenerationValidationError`와 500이 반복된 서버 로그를 공유했다.
- 확인한 내용: 처음에는 일반 `Error`만 기록돼 원인을 알기 어려웠다. 진단을 보강하자 `EXPLICIT_INTENT_AMBIGUOUS`와 `UNSUPPORTED_PERSONAL_DEVICE`가 번갈아 발생했고, 모델 JSON 스키마와 검증 정책도 실제 출력에 비해 엄격했다.
- 바뀐 내용: 제공자 구조화 출력과 Zod 스키마를 맞추고, 로그에는 원문 없이 실패 규칙 ID를 남기도록 했다. 명시 의도와 말투 장치 검증을 실제 입력·관계·강도 정책에 맞게 조정하고 한 번의 안전한 재시도를 추가했다.
- 결과: 답장 실패의 원인을 개인 대화 노출 없이 구분할 수 있게 됐고, 정상 후보가 과도한 규칙 때문에 500이 되는 경우가 줄었다.

### 15. `한 가지만 확인할게요` 재시도 문제를 고쳤다

- 내가 요청하거나 한 행동: 추가 설명을 요구하는 이유와, 설명을 입력한 뒤 `답장 다시 만들기`가 동작하지 않는 이유를 물었다.
- 확인한 내용: 질문은 대명사나 현재 목적이 불명확할 때 잘못된 답장을 만들지 않기 위한 장치였다. 그러나 재시도 때 사용자의 추가 설명이 충분성 판단과 생성 컨텍스트에 제대로 합쳐지지 않는 경로가 있었다.
- 바뀐 내용: 붙여넣은 대화, 상황, 의도와 추가 설명을 최신 현재 턴으로 결합하고, 사용자가 제출한 정보 자체를 충분성 판단에 포함하도록 수정했다.
- 결과: 맥락이 정말 부족할 때만 질문 하나가 나오고, 답변 뒤 재생성이 같은 질문에 갇히지 않게 됐다.

### 16. 두 개발 서버와 오래된 `.next` 캐시 문제를 해결했다

- 내가 요청하거나 한 행동: `Cannot find module './81.js'` 런타임 오류와 디자인 붕괴를 보여주고, 이미 가동 중인 서버의 로그를 어디서 볼 수 있는지 물었다.
- 확인한 내용: 3000번 포트에는 이전 서버가 남아 있었고 새 `pnpm dev`는 3001번에서 실행됐다. 브라우저는 기존 3000번을 보고 있었지만 사용자가 보는 터미널은 새 서버 로그였으며, 빌드와 개발 캐시가 섞여 모듈과 CSS가 깨졌다.
- 바뀐 내용: `lsof`로 3000번 PID를 확인해 기존 프로세스를 종료하고, 모든 서버가 멈춘 뒤 `.next`를 정리한 다음 프로젝트 루트에서 개발 서버 하나만 실행하는 절차로 통일했다.
- 결과: 브라우저와 터미널 로그가 같은 서버를 가리키게 됐고, 누락 모듈과 깨진 디자인이 복구됐다. 이 시점에 로컬 MVP의 주요 실행 장애가 정리됐다.
