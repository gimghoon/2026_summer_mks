# 재개 가능한 대화방 분석 설계

## 목표

대화방 분석 중 모델 또는 저장 단계가 실패하더라도 이미 성공한 청크 분석을 보존한다. 재시도는 미완료 작업만 수행하며, UI는 고정된 가짜 백분율 대신 실제 청크 진행 상태를 표시한다.

## 현재 문제

현재 분석은 청크 구성, 청크별 모델 호출, 임베딩, 주제 종합, 방 요약과 프로필 반영을 하나의 긴 PostgreSQL 트랜잭션 안에서 수행한다. 50개 청크 중 마지막 단계가 실패해도 전체 트랜잭션이 롤백되므로 성공한 모델 호출의 결과가 모두 사라진다. API는 내부 실패를 일반 `503`으로만 반환하고 UI는 45% 또는 65%의 고정 값을 보여 주어 실제 진행 상태를 알 수 없다.

## 설계 원칙

- 원문, 프롬프트, 모델 응답, 참여자 이름은 로그에 남기지 않는다.
- 청크 결과는 출처 지문과 분석 키로 버전 관리한다.
- 청크 단위 작업은 멱등적이어야 한다.
- 방 기억과 프로필은 모든 청크가 준비된 뒤에만 교체한다.
- 재시도는 이미 준비된 동일 지문 청크의 모델 호출과 임베딩을 반복하지 않는다.
- 동일 대화방에 대한 동시 분석은 PostgreSQL advisory lock으로 직렬화한다.

## 상태 모델

청크의 암호화된 분석 payload에 다음 상태를 사용한다.

- `pending`: 청크 경계만 생성되었으며 모델 결과가 없다.
- `prepared`: 청크 분석과 임베딩이 저장됐지만 방 단위 종합은 완료되지 않았다. 기존 `analysisComplete: false`와 대응한다.
- `complete`: 방 단위 종합과 프로필 반영까지 성공했다. 기존 `analysisComplete: true`와 대응한다.

별도 공개 상태 문자열을 DB에 추가하지 않고 기존 암호화 payload의 필드와 출처 지문으로 판정한다. 마이그레이션 없이 기존 불완전 payload도 `pending` 또는 `prepared`로 읽는다.

## 처리 흐름

1. 짧은 트랜잭션에서 advisory lock을 얻고 결정적 청크 파티션을 조정한다.
2. 각 청크에 대해 현재 출처 지문과 저장된 지문을 비교한다.
3. 동일 지문의 `prepared` 또는 `complete` 청크는 모델 호출을 건너뛴다.
4. 필요한 청크만 모델로 분석하고 임베딩을 생성한다.
5. 청크 하나가 성공할 때마다 별도의 짧은 트랜잭션으로 `prepared` payload, 태그, 이벤트, 임베딩을 저장한다.
6. 모든 현재 청크가 `prepared` 또는 `complete`인지 확인한다.
7. 주제 기억과 방 요약을 생성하고 의미적 무결성 검증을 수행한다.
8. 하나의 짧은 최종 트랜잭션에서 AI 프로필 교체, 방 기억 저장, 모든 현재 청크의 `complete` 전환을 원자적으로 수행한다.
9. 최종 단계가 실패하면 청크는 `prepared`로 남아 다음 재시도에서 재사용된다.

청크 파티션 변경으로 폐기되는 분석 키의 정리 계보는 기존 reconciliation 규칙을 유지한다. 새 출처 지문은 이전 `prepared` 결과를 재사용하지 않는다.

## 진행 상태 API와 UI

분석 API의 상태 조회는 다음 비민감 정보만 반환한다.

```json
{
  "status": "pending | analyzing | finalizing | ready | failed",
  "completedChunks": 17,
  "totalChunks": 50,
  "stage": "chunks | hierarchy | profiles | complete"
}
```

클라이언트는 분석 POST를 시작한 뒤 짧은 간격으로 상태를 조회한다. 백분율은 `completedChunks / totalChunks`에서 계산하고 최종 종합 단계는 별도 문구로 표시한다. 분석 버튼은 요청 중 비활성화한다. 페이지를 새로 열어도 서버 상태로 진행률을 복원한다.

## 안전한 운영 로그

`safeLog`를 사용해 다음 스칼라 메타데이터만 기록한다.

- `roomId`
- `stage`
- `completedChunks`
- `totalChunks`
- `failure` — 미리 정의한 코드만 허용
- `providerStatus` — 존재할 때 HTTP 상태 번호

허용할 실패 코드는 `provider_rejected`, `provider_unavailable`, `model_validation`, `evidence_validation`, `hierarchy_validation`, `database`, `unexpected`이다. 예외 메시지는 기록하지 않는다.

## 오류 처리

- 일시적 모델 오류는 기존 한 번 재시도 정책을 유지한다.
- 청크 실패는 해당 청크를 `pending`으로 남기고 API가 안전한 `503`을 반환한다.
- 주제 또는 방 요약의 의미 검증 실패는 청크 결과를 보존하고 최종 단계만 다시 수행한다.
- 프로필/방 기억 최종 저장은 원자적이며 부분 적용되지 않는다.
- 클라이언트 응답은 원문이나 모델 출력을 포함하지 않는다.

## 테스트

- 청크 3개 중 두 번째 모델 호출이 실패하면 첫 번째 청크의 `prepared` 결과가 남는다.
- 재시도는 첫 번째 청크를 건너뛰고 두 번째와 세 번째만 호출한다.
- 출처 지문이 바뀐 `prepared` 청크는 재분석한다.
- 주제 종합 실패 후 재시도는 청크 모델과 임베딩을 다시 호출하지 않는다.
- 최종 프로필 저장 실패는 방 기억과 `complete` 전환을 롤백하지만 `prepared` 청크는 보존한다.
- 상태 조회는 실제 완료 청크 수와 전체 청크 수를 반환한다.
- 로그에는 원문, 프롬프트, 모델 출력과 참여자 이름이 포함되지 않는다.
- UI는 고정 45% 대신 서버의 청크 진행률과 최종화 상태를 표시한다.

## 범위 제외

- 여러 서버 인스턴스 사이의 외부 작업 큐
- 분석 취소 기능
- 이미 실패한 과거 OpenAI 응답 복구
- 모델 비용 예측 또는 결제 관리
